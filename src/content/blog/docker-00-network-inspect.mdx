---
title: "Which network is my container actually on?"
description: "A one-liner that maps every Docker network to its containers, for when two services cannot see each other"
date: "2025-05-09"
tags: ["docker", "networking"]
---

Containers that cannot reach each other usually look like a DNS problem and
usually are not. In a multi-container setup — Compose, or hand-rolled bridge
networks — the common cause is duller: the two containers are simply not on the
same network, so the name resolution that Docker provides *within* a network
never applies.

`docker network inspect` answers this, but only one network at a time, and the
whole question is which network a container ended up on. So loop over all of
them:

```sh
for net in $(docker network ls --format '{{.ID}}'); do
    echo "Network: $net"
    docker network inspect "$net" | jq -r '.[0].Containers[]?.Name'
    echo ""
done
```

- `docker network ls --format '{{.ID}}'` gives bare IDs with no header row, so
  it can be fed straight into the loop.
- `jq -r '.[0].Containers[]?.Name'` pulls just the container names out of the
  inspect output. The `?` matters: it tolerates networks with no containers
  attached, which would otherwise abort the loop with an error.

The output is grouped by network, so you can scan it for the two containers
that ought to be together and check whether they are.

Two things this catches that are easy to miss otherwise: a container attached
to the default `bridge` network instead of the project's own — where Docker's
DNS does not resolve container names at all — and a container quietly attached
to *more* networks than intended, usually left over from an earlier
`docker-compose.yml`.

Once you know which network you want, attaching is one command:

```sh
docker network connect mynetwork mycontainer
```
