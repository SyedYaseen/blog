MQTT is the messaging layer I reach for whenever microcontrollers are involved
— it is publish/subscribe, it is tiny, and an ESP32 can speak it comfortably.
Mosquitto is the reference broker and runs happily in a container.

Most of the difficulty in this setup is not conceptual. It is that the paths
in `docker-compose.yaml`, the paths inside `mosquitto.conf`, and the paths in
the `docker exec` commands all have to agree, and when they do not the broker
starts anyway and simply refuses every connection.

## Compose

```yaml
services:
  mosquitto:
    image: eclipse-mosquitto
    hostname: mosquitto
    container_name: mosquitto
    restart: unless-stopped
    ports:
      - "1883:1883"   # plain MQTT
      - "8883:8883"   # MQTT over TLS
    volumes:
      - ./mosquitto.conf:/mosquitto/config/mosquitto.conf
      - ./certs:/mosquitto/config/certs
      - ./passwd:/mosquitto/config/passwd
      - ./data:/mosquitto/data
```

The `eclipse-mosquitto` image looks for everything under `/mosquitto/config`.
Every path in the config file below is written from the container's point of
view, not the host's.

Create `mosquitto.conf` and the empty `passwd` file **before** the first
`docker compose up`. Docker creates a directory when a bind mount source does
not exist, and the broker then fails on a config file that is a folder.

## Config

```
log_dest stdout

listener 1883
protocol mqtt

allow_anonymous false
password_file /mosquitto/config/passwd

persistence false
```

`log_dest stdout` is what makes `docker logs mosquitto` useful — the default
writes to a file inside the container where you will not look at it.

`allow_anonymous false` is the line that matters. The default is to accept
anyone, and a broker on your LAN with no auth is an open door.

## Passwords

Put one `user:password` per line in `passwd`, in plain text, then have
Mosquitto hash the file in place:

```sh
docker exec mosquitto chown root:root /mosquitto/config/passwd
docker exec mosquitto mosquitto_passwd -U /mosquitto/config/passwd
docker restart mosquitto
```

`-U` means "upgrade this file" — it reads the plaintext lines and rewrites them
hashed. Run it once per new entry. If you run it against an already-hashed file
nothing bad happens, it just does nothing.

The `chown` is there because the broker refuses to read a password file that is
writable by others, the same reasoning SSH applies to private keys.

## Publish and subscribe

```sh
sudo apt install mosquitto-clients

mosquitto_sub -v -t 'hello/topic' -u user -P pwd
mosquitto_pub -t 'hello/topic' -m 'hello MQTT' -u user -P pwd
```

Run the subscriber in one terminal and the publisher in another. `-v` prints
the topic alongside the payload, which is what you want the moment you have
more than one topic in play.

## Self-signed TLS

Unencrypted MQTT sends the password in the clear. On a home network that may be
an acceptable risk; if it is not, sign your own certificates.

```sh
cd mosquitto/certs

# Certificate authority
openssl genrsa -out ca.key 2048
openssl req -new -x509 -days 365 -key ca.key -out ca.crt -subj "/CN=LocalMQTTCA"

# Server key and signing request
openssl genrsa -out server.key 2048
openssl req -new -out server.csr -key server.key -subj "/CN=localhost"

# Sign the server cert with our own CA
openssl x509 -req -in server.csr -CA ca.crt -CAkey ca.key -CAcreateserial \
  -out server.crt -days 365
```

The `CN` on the server certificate has to match the hostname clients connect
to. `localhost` works for local testing; use the LAN hostname or IP if devices
are connecting across the network, or the handshake fails on name mismatch.

Add a TLS listener to the config:

```
listener 8883
protocol mqtt

cafile   /mosquitto/config/certs/ca.crt
certfile /mosquitto/config/certs/server.crt
keyfile  /mosquitto/config/certs/server.key

require_certificate false
```

Then connect with the CA file so the client can verify the chain:

```sh
mosquitto_sub -h localhost -p 8883 \
  --cafile ./mosquitto/certs/ca.crt \
  -t 'hello/topic' \
  -u user -P pwd \
  --insecure
```

### Why require_certificate is false

It controls whether the *client* must present a certificate:

- `false` — server-side TLS only. The connection is encrypted and the client
  verifies the broker, but the broker identifies clients by username and
  password.
- `true` — mutual TLS. Every client needs its own certificate signed by the CA.
  Genuinely more secure, and worth it on a locked-down internal network.

Most MQTT clients — `mqtt.js`, off-the-shelf IoT devices — have no way to
present a client certificate, so `false` is the practical setting. You still
get encryption; you just are not using certificates for client identity.

### Why rejectUnauthorized: false in a Node client

This tells the Node.js client not to reject an untrusted certificate. Because
the CA above is one you invented, nothing in the system trusts it by default,
and Node refuses the connection. Two ways out:

1. Pass the CA explicitly — `ca: fs.readFileSync('ca.crt')` — so the client can
   verify the chain properly. **This is the one to use.**
2. Set `rejectUnauthorized: false`, which skips verification entirely.

Option 2 disables the check that stops someone impersonating your broker, so it
is a debugging tool, not a setting. With a certificate from a real CA like
Let's Encrypt you omit both and it just works.

## Debugging

Check the broker is listening on the ports you think it is:

```sh
docker exec mosquitto netstat -tuln
docker logs mosquitto
```

If connections are being refused, temporarily set `allow_anonymous true` and
retry. If it connects, the problem is the password file — wrong path, wrong
permissions, or never hashed. If it still fails, the problem is networking or
TLS, and you have halved the search space.
